Technical deep dive

How V2 is put together.

Obsisphere is a web application living inside a Minecraft plugin. The important engineering problem is not making a dashboard render; it is moving between browser work, server-side HTTP work, persistent state and Minecraft-thread-affine operations without turning the game server into a control-panel benchmark.

Language / runtime

The backend is Java and runs as a Bukkit/Paper-compatible plugin. The current build workflow targets JDK 21.

Web layer

The plugin embeds its own HTTP serving layer for the frontend and JSON APIs instead of requiring a separate Node service.

Frontend

Vanilla HTML, CSS and JavaScript, deliberately avoiding a framework dependency for the panel shell.

Specialized rendering

The live map is WebGL-based, uses worker-side processing and derives render assets from Minecraft/resource-pack content.

Persistence

Audit and player-activity history are database-backed. Other durable panel configuration uses server-side structured files where appropriate.

Browser cache

Map chunks use IndexedDB for persistent client-side caching while runtime chunk payloads and GPU resources are bounded separately.

Request lifecycle

Browser action → permission check → server-safe execution.

Administrative actions pass through authenticated handlers, permission gates and CSRF checks. Work that touches Bukkit state returns to the Minecraft server thread where thread affinity requires it, while expensive I/O should stay away from that thread.

01

Authenticate

Session cookies establish the panel identity after bootstrap/login and 2FA requirements.

02

Authorize

Page visibility is not the security boundary; handlers enforce the relevant permission server-side.

03

Protect changes

State-changing requests use CSRF validation and strict request parsing/bounds.

04

Dispatch work

Filesystem/network work and Minecraft runtime work are separated according to what the operation needs.

05

Audit

Sensitive panel actions are recorded with actor, action and endpoint context.

06

Notify

Selected audit/player events can surface through realtime toast notifications for connected admins.

Authentication & access

Security features are part of the product model.

Account lifecycle

First run uses an expiring bootstrap flow for the master account. Managed users can be forced through password change and TOTP registration before normal panel use. Sessions are invalidated on logout and protected state changes use CSRF tokens.

Live 3D map internals

The map is its own subsystem.

V2 streams chunk payloads, turns block/palette data into browser-renderable geometry, uses resource-pack-derived textures/models and keeps a persistent browser cache so revisiting explored areas does not automatically mean downloading everything again.

DATA

Chunk payloads

Server endpoints expose chunk data and revisions to the browser instead of shipping screenshots.

GPU

WebGL renderer

Terrain sections and models are rendered client-side, with LOD/runtime buffer management.

CACHE

IndexedDB

Persistent chunk entries are byte-accounted and pruned oldest-first when cache size crosses its target.

ASSETS

Resource-pack fingerprinting

Static Minecraft render assets are versioned by fingerprint and cached until the resource pack changes.

LIFE

Lifecycle control

Leaving the map or hiding the browser tab suspends map rendering/polling work instead of keeping it alive in the background.

STATUS

Performance pass ongoing

Remaining work is mostly around polling cadence, main-thread encoding, SSE/journal efficiency and long-tail cache behavior.
